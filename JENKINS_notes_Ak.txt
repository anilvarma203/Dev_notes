=>CI-CD is the set of practices that automate the software development and deployment process.

CI:(Continuous Integration)
===
CI is a software development practise that involves Developers frequently merging their code changes into a shared/central repository and it detects the change, and runs automated build and tests.
             CI = Continuous build + continuous test

                   push           build/tests
         developer------->GitHub---------------->CI server
           code
=>The goal of CI is to improve software quality, early bug detection, faster development, quick feedback.
        

CD:(Continuous Delivery/Continuous Deployment): both refer to automating the process of getting new code changes into production, but they differ in their levels of automation,

Continuous Delivery:
=====================
code is automatically tested and ready to be deployed to production at any time.
After a developer finishes coding, the system automatically build, tests, and prepares the code for release. However, the actual deployment to production still requires manual approval.
          
            Developer ---> GitHub ---> Dev (Auto Deploy) ---> QA (Auto Deploy) ---> PreProd (Auto Deploy) ---> Prod (Manual Approval Required)
                      
• Auto Deploy: Code moves automatically without manual intervention.
• Manual Approval Required: Deployment to Production requires human approval.

Continuous Deployment:
========================
code is automatically deployed to production without any manual interactions.
After code passes all the tests,it is automatically deployed/pushed to production—no manual approval needed.
       
            Developer ---> GitHub ---> Dev (Auto Deploy) ---> QA (Auto Deploy) ---> PreProd (Auto Deploy) ---> Prod (Auto Deploy)

Key Difference:
• In Continuous Delivery, Prod requires manual approval.
• In Continuous Deployment, everything is deployed automatically—including Prod.

🚀Advantages of Continuous Delivery:
---------------------------------------
1. Faster Time to Market
2. Improved Product Quality
3. Reduced Deployment Risk
4. Easier rollbacks
5. Continuous feedback

=>alternative ways to automatically fetch code into Jenkins without using webhooks,
1.Build periodically:
-----------------------
🕒 How to Set Up “Build Periodically” in Jenkins
• Go to your Jenkins job
     >Click on the job name → Configure

• Scroll to “Build Triggers”
    >Check ✅ Build periodically

• Enter a cron expression in the “Schedule” box
Example:                                                                                              
Code
H/15 * * * *   # Every 15 minutes
• click on save.

2.Poll SCM:
-----------
Jenkins can periodically check your Git repo for changes using SCM polling.

🔁 How Poll SCM Works Without Webhook
=>Jenkins will periodically check your Git repository for changes.
=>If it detects a new commit, it will trigger the job and pull the latest code.
=>If there are no changes, Jenkins skips the build.

How to set it up:
• In your Jenkins job, go to Build Triggers
   >Check ✅ Poll SCM

• Enter a cron schedule like:
Code
H/5 * * * *   # Polls every 5 minutes

NOTE:
If you want to schedule builds based on code changes instead, you’d use Poll SCM or webhooks. But for time-based automation, “Build periodically” is your go-to.

🔍 Comparison Table:

Trigger Type      :       How It Works                                                   : When It Runs               : Efficiency                    : Use Case Example

Build Periodically | Runs the job at fixed time intervals using cron syntax         | Always at scheduled times | ❌ May run even if no changes | Nightly builds or maintenance
Poll SCM           | Jenkins polls the repo at intervals; runs only if changes found| Only if changes are found | ⚠️ Uses resources for polling | CI for infrequent commits
Webhook            | Repo sends real-time notification to Jenkins on code push      | Instantly after a commit  | ✅ Most efficient trigger     | Real-time CI/CD development

2.This Project Is Parameterized: that allows you to define input parameters for your job—making it dynamic and reusable.
🧹 What It Means
  • When you check “This project is parameterized”, Jenkins lets you:
  • Define parameters that users or scripts can provide when triggering the job
  • Customize job behavior based on those inputs

🧪 Examples of Parameters You Can Add,
  • Boolean Parameter  :  when you have two options we use this.                          eg: on/off or true/false 
  • Choice Parameter   :   when you have multiple options.                                eg: dev, test, prod
  • Credential Parameter:  uesd to store credentials and lets users select a credential from a dropdown when starting a build manually.
                                                                                           eg: Authenticating to private Git repositories.
  • String Parameter   :  A String Parameter lets users enter a line of text when triggering a build.
                                                                                           eg: branch name, version number ENV=staging or VERSION=1.2.3
  • File Parameter     :  Users upload a file when starting a build.                       eg: from local server to jenkins server.

Triggers
---------
1. Build after other projects are built: 
🔁 What It Means in Context,
    • This setting allows you to trigger this job (job1) automatically after one or more other Jenkins jobs complete their builds. It’s part of Jenkins' build chaining mechanism, useful for orchestrating multi-step pipelines.
🧩 How It Works:
When you enable “Build after other projects are built”, you’ll be prompted to:
   • Enter the names of upstream jobs (e.g., compile-job, test-suite)
   • Jenkins will monitor those jobs, and once they are built (i.e., finish execution), it will trigger job1
=>This is especially useful when:
    • You want to run a deployment job after tests pass
    • You’re chaining multiple jobs in a CI/CD pipeline
    • You’re managing dependencies between projects
